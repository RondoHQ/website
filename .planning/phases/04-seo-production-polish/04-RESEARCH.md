# Phase 4: SEO & Production Polish - Research

**Researched:** 2026-02-06
**Domain:** SEO, analytics, accessibility, performance optimization
**Confidence:** HIGH

## Summary

Phase 4 focuses on making the Rondo website discoverable, measurable, and accessible. The research covers Astro's native SEO capabilities, Plausible Analytics integration, WCAG 2.1 AA compliance, and Cloudflare Pages optimization patterns.

**Key findings:**
- Astro has official `@astrojs/sitemap` integration and strong SEO support through ecosystem packages
- Plausible Analytics provides cookieless tracking with simple script integration and custom event support
- WCAG 2.1 AA requires 4.5:1 contrast for normal text; glass morphism implementations need special attention
- Cloudflare Pages provides automatic caching and compression; custom headers via `_headers` file
- Lighthouse and axe-core provide complementary accessibility testing (automated + manual needed)
- The existing codebase already implements `prefers-reduced-transparency` but lacks `prefers-reduced-motion`

**Primary recommendation:** Use Astro's official `@astrojs/sitemap`, add `astro-seo` package for meta tags, implement JSON-LD manually with schema-dts for type safety, integrate Plausible via script tag in BaseLayout, and verify accessibility with Lighthouse + manual keyboard/screen reader testing.

### Pattern 4: Accessibility - prefers-reduced-motion

**What:** Disable or simplify animations for users with vestibular motion disorders.

**When to use:** For all hover effects, transitions, and transforms (CONTEXT.md requirement).

**Example:**

```css
/* Default: smooth transitions */
.btn-primary {
  transition: all 0.2s ease;
}

.btn-primary:hover {
  transform: translateY(-2px);
  box-shadow: 0 10px 20px rgba(34, 211, 238, 0.3);
}

/* Accessibility: disable motion */
@media (prefers-reduced-motion: reduce) {
  .btn-primary {
    transition: none;
  }

  .btn-primary:hover {
    transform: none; /* Remove translateY */
    /* Keep color/shadow changes - they're not motion */
  }
}
```

**Current status:** The codebase already implements `prefers-reduced-transparency` for glass morphism but lacks `prefers-reduced-motion` for transitions.

### Pattern 6: Cloudflare Pages Headers

**What:** Configure security and caching headers via `_headers` file.

**When to use:** For security headers, asset caching, and CSP (if needed).

**Example:**

```
# public/_headers

# Security headers for all pages
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin

# Cache static images (not hashed, so use shorter cache)
/rondo-logo.png
  Cache-Control: public, max-age=86400

/og-image.png
  Cache-Control: public, max-age=86400
```

**Note:** Cloudflare Pages has aggressive default caching. Avoid custom `Cache-Control` for HTML/CSS/JS unless assets have content hashes in filenames.

### Anti-Patterns to Avoid

- **Separate OG image per page:** User decision specifies single branded OG image (logo + tagline on dark background), not per-page screenshots.
- **Cookie consent banner:** Plausible is cookieless — adding a banner creates friction for no legal reason.
- **Lighthouse 100 score obsession:** Perfect scores don't guarantee usability. Focus on actual performance (< 3s load) and manual a11y testing.
- **Inline styles for critical CSS:** Astro's build already optimizes CSS. Premature optimization adds complexity.
- **Third-party font CDN:** Current site uses system fonts (`system-ui`) — optimal for performance, no custom fonts needed.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Sitemap generation | Custom XML builder | `@astrojs/sitemap` | Handles multi-page sites, updates automatically, supports i18n |
| OpenGraph meta tags | Manual `<meta>` tags | `astro-seo` | Validates required OG properties, prevents duplicate tags |
| JSON-LD schemas | Plain objects | `schema-dts` types | Type safety catches schema errors at compile time |
| robots.txt logic | Static file + comments | `astro-robots-txt` | Auto-links sitemap, handles build-time conditionals |
| Contrast checking | Eyeballing colors | WebAIM Contrast Checker | WCAG compliance requires accurate ratio calculations |
| Analytics events | Custom beacon API | Plausible `plausible()` function | Handles queuing, retries, and respects DNT |
| Accessibility audit | Manual HTML review | Lighthouse + axe-core | Catches 30-40% of issues automatically, standardized WCAG mapping |

**Key insight:** SEO and accessibility have many subtle requirements (e.g., OG requires all 4 basic properties, WCAG has specific contrast ratios). Libraries encode this expert knowledge and prevent common mistakes.

## Common Pitfalls

### Pitfall 1: Missing `site` Configuration in astro.config.mjs

**What goes wrong:** `@astrojs/sitemap` silently fails or generates invalid URLs without the `site` property.

**Why it happens:** Astro doesn't enforce `site` at build time; sitemap integration expects it.

**How to avoid:** Always set `site` in `astro.config.mjs` before adding sitemap integration:

```javascript
export default defineConfig({
  site: 'https://rondo.club',
  integrations: [sitemap()]
});
```

**Warning signs:** Build succeeds but sitemap-index.xml contains localhost URLs or relative paths.

### Pitfall 2: Contrast Ratio Failures with Glass Morphism

**What goes wrong:** White text on glass surfaces may fail WCAG AA (4.5:1) when background images bleed through transparency.

**Why it happens:** `backdrop-filter: blur()` and `rgba()` backgrounds reduce effective contrast depending on underlying content.

**How to avoid:**
- Use WebAIM Contrast Checker with worst-case background colors (darkest parts of hero image).
- Prior decision already established: "Pure white text on glass surfaces — WCAG 4.5:1 contrast compliance"
- Current implementation uses `rgba(255, 255, 255, 0.05)` backgrounds with white text — verify this meets 4.5:1 in production.
- The `prefers-reduced-transparency` media query fallback (`background: rgba(255, 255, 255, 0.15)`) improves contrast for users who need it.

**Warning signs:** Lighthouse accessibility audit flags low contrast; text hard to read in certain lighting conditions.

### Pitfall 3: Plausible Script Tag Placement

**What goes wrong:** Plausible doesn't track page views or custom events fail silently.

**Why it happens:** Script placed at end of `<body>` instead of `<head>`, or `window.plausible` function not defined before first event.

**How to avoid:**
- Place script in `<head>` with `defer` attribute.
- Define `window.plausible` polyfill before any components that might trigger events:

```html
<script defer data-domain="rondo.club" src="https://plausible.io/js/script.js"></script>
<script>
  window.plausible = window.plausible || function() {
    (window.plausible.q = window.plausible.q || []).push(arguments)
  }
</script>
```

**Warning signs:** Plausible dashboard shows no activity; console errors `plausible is not defined`.

### Pitfall 4: OpenGraph Image Dimensions

**What goes wrong:** OG image appears cropped or blurry when shared on social media.

**Why it happens:** Platforms have different preferred dimensions; too small = upscaling, too large = file size bloat.

**How to avoid:**
- Use 1200×630 pixels (16:9 aspect ratio) — the universal standard across Facebook, Twitter, LinkedIn.
- Keep file size under 5MB, prefer JPG or PNG (not WebP — LinkedIn doesn't support it).
- User decision specifies: "Custom branded OG image: logo + tagline on dark background"

**Warning signs:** Image cropped awkwardly in social media previews; different appearance across platforms.

### Pitfall 5: Missing Alt Text on Decorative Images

**What goes wrong:** Screen readers announce "image" without context, or read filename (e.g., "rondo-logo.png").

**Why it happens:** Developers forget `alt` attribute or use filename as fallback.

**How to avoid:**
- Decorative images: `alt=""`
- Functional images (logos, icons): Descriptive text like `alt="Rondo logo"`
- Hero screenshots: Contextual description like `alt="Rondo dashboard showing team overview and member list"`

**Warning signs:** Lighthouse flags missing alt text; screen reader testing reveals confusing announcements.

### Pitfall 6: Keyboard Navigation Traps

**What goes wrong:** Focus gets stuck in modal/menu or can't reach interactive elements.

**Why it happens:** Custom JavaScript components don't manage focus correctly; `tabindex` misused.

**How to avoid:**
- Test navigation with Tab/Shift+Tab through entire page flow.
- Ensure visible focus indicators (`:focus` styles) on all interactive elements.
- Current forms use native `<input>`, `<textarea>`, `<button>` — these have built-in keyboard support.

**Warning signs:** Can't Tab to submit button; focus disappears; Tab order doesn't match visual layout.

### Pitfall 7: Over-Reliance on Automated Accessibility Testing

**What goes wrong:** Site passes Lighthouse 100 accessibility but fails real user testing.

**Why it happens:** Automated tools catch only 30-40% of WCAG issues — color contrast, alt text, ARIA roles. They miss logical tab order, screen reader UX, cognitive accessibility.

**How to avoid:**
- Use Lighthouse/axe-core as first pass, not final validation.
- Manual testing: keyboard-only navigation, screen reader (VoiceOver on Mac, NVDA on Windows), zoom to 200%.
- CONTEXT.md specifies full audit: "contrast, alt text, form labels, semantic HTML, keyboard navigation, focus indicators, screen reader flow, skip links"

**Warning signs:** Automated tests pass but users report accessibility issues.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Manual `<meta>` tags | `astro-seo` component | 2023+ | Validates required OG properties, prevents duplicates |
| Static robots.txt | `astro-robots-txt` integration | 2022+ | Auto-links sitemap, build-time logic |
| Google Analytics | Plausible/Fathom | 2020+ | Privacy-first, no cookie consent needed, GDPR-friendly |

**Deprecated/outdated:**
- **Google PageSpeed Insights API v4:** Use Lighthouse CLI directly (v10+) or PageSpeed Insights v5+ API
- **astro-seo-meta:** Abandoned package; use `astro-seo` instead
- **Plausible `plausible-tracker` npm package:** Use direct script tag integration for simpler setup
- **WCAG 2.0:** Sites should target WCAG 2.1 AA minimum (2.2 AAA is latest but AA is standard)
